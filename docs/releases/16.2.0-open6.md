# GFOpenAmigaGCC 16.2.0-open6

GCC 16.2 for AmigaOS 3.x (`m68k-amigaos`) and AROS 68k (`m68k-aros`). Everything in open4 remains. Open6 is the first published release since open4 (open5 was prepared on 2 November 2026 and went into AmiCradle's `os32-gcc16` stove, but was never published), so these notes list open5's changes and open6's.

Open6 is one compiler for both 68k targets. The `m68k-aros` target joins: stock GCC 16.2.0 with AROS's own diffs and the m68k fixes this repository carries, so AROS code and GFOpenKick's exec (an AROS module) get the late-combine fix (PR123853, open4's `patches/gcc/0013`) that AmiCradle's `aros68k-gcc16` stove lacked. The `m68k-amigaos` compiler is open5's but for its identity.

## New since open4

| Item | open4 | open6 |
| --- | --- | --- |
| Name and identity | `OpenAmigaGCC 16.2.0-open4`; `openamigagcc-*` tarballs | `GFOpenAmigaGCC 16.2.0-open6` for both targets (`patches/amiga-gcc/0002-open6-pkgversion.patch`, `scripts/build-aros.sh`); `gfopenamigagcc-*` tarballs, the source tarball holding this repository as `gfopengcc/` (open5's renaming) |
| `m68k-aros` (AROS 68k) | not here: AmiCradle's `aros68k-gcc16` stove, stock GCC 16.2.0 and AROS's diff only, built by AROS's crosstools build | `scripts/fetch-aros.sh` and `scripts/build-aros.sh`: stock GCC 16.2.0, binutils 2.47 and isl 0.27 (`scripts/aros.lock`), AROS's diffs as AROS has them, and `patches/gcc` 0003, 0005, 0013 and 0014 as they are and 0008 ported (`patches/aros/series`, [docs](../aros.md)) |
| exec's `oe_AlertText` (`exec_alert.c` before amicradle-guest #582) at `-m68040 -O2`, `m68k-aros` | `move.b (a1)+,(0,a1,d0.l)`: each byte one place late | `lea` into a register of its own, then `move.b (An)+,(Am)` |
| `libamiga.a` (GFOpenNDK) in the 68000 multilibs | built for the 68040 and copied into every multilib folder: a `-m68000` program calling `RangeRand`, `ArgArrayInit` or another helper got 68020 instructions | built once per multilib with its own flags; `build.sh` checks the 68000 folders for 68020 code ([docs](../openndk-libamiga.md)) (open5) |
| A program whose thread crashed (a CPU exception leaves its task in `Wait(0)`) | never returned to the Shell: exit joined every thread and waited for ever | exit leaves a crashed thread behind and returns: `patches/aros-stuff/0007` (open5) |
| `pthread_cond_timedwait` with an absolute time already past | waited for ever | times out at once: `patches/aros-stuff/0007` (open5) |
| `__thread`/`thread_local` and pthread keys in a task pthreads did not make (an SDL thread from `CreateNewProc`/`NP_Entry`, a Workbench helper) | `pthread_self()` gave an id with no record and `pthread_getspecific()` read `NULL->tlsvalues` (Kraptor's SDL thread wrote to $02002F3C on GFOpenKick) | the task gets a record and TLS block of its own on its first pthreads call, reclaimed (key destructors run) once it has ended; with the table full it is the main thread; never a NULL record: `patches/aros-stuff/0008`, `0009` (`tests/pthreads/foreigntls.c`) (open5) |
| A check that read a whole list with `grep -q` under `pipefail` (`build.sh`'s GFOpenNDK `libamiga.a` and `trap #7` checks, `package.sh`'s) | could fail, or pass, at random: `ar`/`objdump` killed by SIGPIPE once `grep` had its match | `grep` reads the whole list |
| Checks | | `tests/autoinc/check.sh` scans both targets' code for PR123853 with amicradle-guest's `scan_autoinc_overlap.py`; `tests/aros-series.sh` keeps every GCC patch decided for `m68k-aros`; `tests/release-names.sh` keeps the names in step |

Open1 to open4 stay as they were published: their tarballs keep the `openamigagcc-` names and their compilers say `OpenAmigaGCC`. Tools that find a toolchain by its tarball name or its `--version` line should accept both.

The `m68k-amigaos` target libraries open6 builds are open5's: on the Cradle machine every one compared equal to the open5 `os32-gcc16` stove's except for debug information and `assert` file names, which name the build folder; the open ROM built with open6 for both targets is byte for byte the one built with open5 and `aros68k-gcc16`.

The `m68k-aros` compiler is not in the release tarball: it needs an AROS SDK (from an AROS build) as its sysroot, so it is built on the machine that has one (AmiCradle's `aros68k-gcc16` stove from open6). Its complete source and recipe are in the source tarball.

## Checked with

The release is built and published by this repository's `build` workflow (run by hand with `release: 16.2.0-open6`). The tarballs are published only if every check in that same run passes, the `aros` job's too:

- `tests/release-names.sh 16.2.0-open6`: the identity patch, `build.sh`'s and `build-aros.sh`'s identity, the tarball names and these notes agree, before anything is built.
- A complete build from `scripts/sources.lock` with every patch, and `build.sh`'s own checks: the open6 identity, no `libm881` for soft-float `-m68040`, no `trap #7` for a read of address 0, C and C++23 programs link with libnix, every multilib links its own GFOpenNDK `libamiga.a`, and the 68000 ones have no 68020 code.
- `tests/repro/prove.sh`, plain and with `-fno-tree-loop-distribute-patterns`, under `qemu-m68k`, and `tests/autoinc/check.sh --amigaos`.
- `tests/libnix/endptr/run.sh`, `tests/cxx/lean-check.sh` and `tests/baserel/eh-check.sh`.
- A compile of the tests that need a real AmigaOS (`tests/cxx`, `tests/pthreads`, `tests/libnix`); running them stays a lab job.
- The `aros` job: `tests/aros-series.sh`, `m68k-aros-gcc` built without an AROS SDK, and `tests/autoinc/check.sh --aros`: no move addresses its destination through the register its source steps, for every CPU at `-O2`, `-O3` and `-Os`.
- `scripts/package.sh`: no NDK file in either tarball, and every `libamiga.a` is GFOpenNDK's.

## Known

- The toolchain needs glibc 2.38 or later.
- The shared `libnix4.library` still does not link; normal static programs do not need it.
- For ARM64 Linux, use 16.2.0-open1's toolchain until an ARM64 build of a later release is made.
- A work folder that built open4 or open5 already has that release's identity patch in amiga-gcc's `Makefile`, so open6's does not apply there: build from a fresh `scripts/fetch.sh` work folder (CI always does).
- `m68k-aros`: a C++ program linked with `-m68040` is left with `__divsi3` undefined (as with the `aros68k-gcc16` stove); link C++ at the default CPU, with `-Wl,-u,__pthread_Init_Func -lpthread -latomic` as the stove's tests do.
